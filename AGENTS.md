# KaadzOS Project Brief

KaadzOS is a Debian 13 (trixie) amd64 live and installable distribution built with live-build.

## Principles

- Keep the base ISO minimal: disable APT recommends, use short package lists, and provide heavy features only through on-demand packs.
- Use a polished, dark, high-contrast interface built around Sway and Wayland.
- Build and test entirely in GitHub Actions. Do not assume the development machine can build an ISO or run a VM.
- Use Cloudflare only for hosting: R2 for ISOs and the APT repository, and Pages for the website. Do not require servers.
- Do not use Hyprland because it is not in Debian stable.
- Verify every new package exists in trixie before adding it, using packages.debian.org, Debian's package API, or `apt-cache` in a trixie container.

## Operating Loop

For every implementation task:

1. Make the change and commit it.
2. Push the commit and trigger the relevant workflow. Pushes to `main` that touch build inputs trigger `build.yml` automatically (as well as the manual `workflow_dispatch` entry point); pushes that only touch `site/`, `docs/**` or Markdown skip the ISO matrix, while `v*` tags always run it in full.
3. Watch the run and inspect failures with the GitHub API or `gh run view --log-failed`.
4. Fix, commit, and repeat until CI is green.

Do not ask the user to paste logs. Do not begin a later phase until the current phase passes CI. Consult the live-build manual and actual build output when behavior is uncertain instead of guessing.

## Decisions

- Distribution and architecture: Debian trixie, amd64.
- Image format: hybrid ISO with Syslinux for BIOS and GRUB for UEFI.
- Installer: excluded from the Phase 1 image; installation support is planned for Phase 5.
- Package policy: `--apt-recommends false`; archive areas are `main contrib non-free-firmware`.
- Root filesystem: squashfs using zstd level 10 to favor CI build time while retaining useful compression.
- Base desktop packages: Linux kernel, Debian firmware, NetworkManager, Sway, Waybar, Foot, Xwayland, Fuzzel, and DejaVu fonts.
- Artifact naming: `KaadzOS-trixie-amd64.iso` with a sibling SHA-256 checksum file.
- Boot validation: QEMU tests both Syslinux BIOS and GRUB/OVMF UEFI boots, preferring KVM and falling back to TCG.
- Session readiness: CI requires a successful Sway IPC query, emits `KAADZOS_SWAY_READY` on the serial console, and captures a screenshot. It also fails the boot test if a `swaynag` process is present, since that means the Sway config emitted errors or warnings (for example an overwritten binding).
- Palette: the "AMOLED" palette in `theme/palette` is the single source of truth; `theme/generate.sh` renders every themed config (Sway, Waybar, foot, fuzzel, mako, swaylock, GTK/Qt, wallpaper, boot splash and Calamares branding) from it. True `#000` background, white primary text and a white accent, with neutral near-black surfaces and near-neutral terminal slots; it matches the website's editorial black-and-white look rather than using a cyan/blue cast. Red is reserved for errors and urgent state.
- Pack CLI: `kaadzos` is POSIX sh (dash-compatible) at `/usr/local/bin/kaadzos`, not Python or Go. The base image has no language runtime and apt-recommends is off, and the CLI only orchestrates apt/dpkg/curl, so a shell script adds no runtime payload or build toolchain.
- Pack format: the repo-root `packs/<name>.pack` files are canonical and declarative (`key=value`: `name`, `description`, `size`, `requires`, `apt`, `repo-url`, `repo-suite`, `repo-components`, `repo-key`, `hook`). CI stages them into `config/includes.chroot/usr/share/kaadzos/packs` before `lb build`; the staged copy is gitignored so the sources stay single-source.
- Pack manager behaviour: `add`/`remove` are idempotent and escalate with `sudo -E` only when needed; `list`/`status`/`addons` never require root; `update` refreshes indexes and upgrades. `KAADZOS_PACKS_DIR`, `KAADZOS_STATE_DIR`, `KAADZOS_DRY_RUN=1` (or leading `--dry-run`) support testing and alternate installs, with install state kept in `$KAADZOS_STATE_DIR/installed`.
- Third-party repos: packs may add a signed apt repo (android uses Waydroid's trixie repo and key) or fetch a static binary (cloudflare, architecture-matched). The CLI detects armored vs binary keys instead of assuming one format.
- Live sudo: the live user `kaadzos` gets NOPASSWD sudo from a build-time hook so pack installs work without a password in the live session; this is live-only and must be removed by the installer in Phase 5.
- Installer launch: the supported entry is `kaadzos-install` (Waybar **Install** button, `$mod+i`, or the "Install KaadzOS" fuzzel entry), which preserves the Wayland environment and pins `-c /etc/calamares`; the Debian `calamares.desktop` entry is hidden in the live image because its `pkexec calamares` path cannot work in this Sway session.
- Add-ons UI: `$mod+a` runs `kaadzos addons`, a fuzzel menu that lists packs and installs/removes them in a terminal.
- Pack validation: the `pack-test` CI job runs `ci/test-packs.sh` in a trixie container to resolve every pack (apt names, repo fields, hooks) and exercise the CLI's dry-run, gating, idempotency and error paths without building an ISO.
- Boot splash: a script-based Plymouth theme (the `script` plugin ships in core `plymouth`; two-step/label plugins are not needed) is generated from the palette by `theme/generate.sh` into `/usr/share/plymouth/themes/kaadzos`; `/etc/plymouth/plymouthd.conf` pins `Theme=kaadzos`, a chroot hook runs `plymouth-set-default-theme` + `update-initramfs`, and a `kaadzos-quit-plymouth` unit ordered `Before=getty.target` (plus getty@tty1/greetd drop-ins and a defensive `plymouth quit` in the session wrapper) hands the display back before any session competes for DRM. The `splash` kernel argument is on both the live append and the installed `kernel_params`.
- Boot menus: no binary hooks — live-build (1:20250505+deb13u1) copies `config/bootloaders/{grub-pc,syslinux_common,isolinux}/` overrides after its templates, and one `config/bootloaders/splash.svg` is rendered by live-build into ISOLINUX 640×480 and GRUB 800×600 splash PNGs. GRUB waits 5 s, ISOLINUX 10 s, the installed system 1 s.
- Browser and defaults: `epiphany-browser` (GNOME Web) is the lean default browser — WebKitGTK renders natively on Wayland and it is the smallest full-featured browser in trixie; Thunar, Mousepad, imv and zathura+zathura-pdf-poppler are the lean file/text/image/PDF defaults, wired by skel `mimeapps.list` and `user-dirs.dirs` (`xdg-user-dirs` package). Screen recording is `kaadzos-record`, a wf-recorder toggle saving `~/Videos/KaadzOS-*.mp4`, bound to `$mod+Print`.
- Memory: `zram-tools` provides a zstd zram swap sized at 50% of RAM, paired with `vm.swappiness=180` and `vm.page-cluster=0` in `/etc/sysctl.d/40-kaadzos-mem.conf`; the boot test emits `KAADZOS_IDLE_RAM` (used/total/zram devices and size) to the serial log and the runner prints it per firmware.
- Secure Boot: the base image ships `shim-signed` + `grub-efi-amd64-signed`, so the installed system's `grub-install` uses Debian's signed GRUB and shim; the live ISO's own GRUB is unsigned and boots with Secure Boot disabled.
- Releases are tag-driven and fully gated: pushing `v*` runs the whole matrix, and the `release` job (`if: startsWith(github.ref, 'refs/tags/v')`, `needs: [build, pack-test, repo-test, boot-test, install-test]`) re-runs `sha256sum --check` on the downloaded artifact before publishing `KaadzOS-trixie-amd64.iso`, `.sha256`, the signed `.sha256.asc` and the public key. Notes come from `docs/release-notes/<tag>.md` (fallback: generated notes). An existing release is refreshed with `gh release upload --clobber` + `gh release edit`, so re-running a tag refreshes the release safely, although a rebuilt ISO may not be byte-identical. A re-run uses the workflow file from the tag's commit, so jobs added later on `main` (such as `apt-repo`) require a new tag from current `main`; moving an existing release tag is not supported.
- Hosting is Cloudflare-only and credential-gated: Cloudflare Pages project `kaadzos` serves the website at https://kaadzos.pages.dev in the account selected by `CLOUDFLARE_ACCOUNT_ID`, and `.github/workflows/site.yml` deploys on `site/**` or `iso-site/**` pushes only when `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` secrets exist (otherwise it logs a notice and stays green). The site is a small React 19 + Vite build in `site/`: `npm ci && npm run build` produces `site/dist/`, which is what Pages deploys; the build runs even without Cloudflare credentials so a broken site fails CI. The editorial page remains hand-authored in `site/index.html` and `site/style.css`, with a self-hosted Inter Tight variable font (OFL, `site/public/fonts/`) and two vendored React Bits accents (`site/src/components/GradientASCII.*` at the top, `TechText.*` above the footer) mounted by `site/src/main.jsx`. Both mount points keep static fallback markup, so the page still reads without JavaScript. `site/public/_headers` sets `default-src 'none'`, `script-src 'self'`, `style-src 'self' 'unsafe-inline'` (React and TechText set inline styles), `font-src 'self'` and images from self plus the CI screenshot host. The vendored React Bits files are MIT + Commons Clause, Copyright (c) 2026 David Haz; the full notice is in `site/src/components/LICENSE.md`.
- R2 public origin: the exact hostname https://iso.kaadzos.pages.dev is a Pages **preview branch alias** on branch `iso` of the `kaadzos` project, not a custom domain or nested DNS record. `site.yml` deploys `iso-site/` with `--branch iso`; `iso-site/_worker.js` runs in advanced mode, serves `/` from the static landing page and `/health` from the Worker, and streams every other path directly from the private R2 bucket through the project's `R2_BUCKET` binding. This avoids `r2.dev` rate limits and a domain purchase; the trade-offs are the Workers free-tier request budget (100,000/day) and streaming rather than edge-caching a 1.4 GB ISO (the CDN cache limit is 512 MB). The production `site/dist/` stays static and Worker-free, so https://kaadzos.pages.dev is unaffected.
- The release job also mirrors assets to Cloudflare R2 when `CLOUDFLARE_ACCOUNT_ID`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` are configured (bucket from `vars.R2_BUCKET || kaadzos`), writing `releases/<tag>/` through the S3-compatible endpoint; without them the step logs a notice and exits 0. R2 is enabled and the `kaadzos` bucket exists with Public Access disabled; all upload credentials are configured, and the v0.1.0 re-run (42366299998) mirrored the ISO under `releases/v0.1.0/` (1,432,977,408 bytes, range requests return 206). The bucket is exposed at https://iso.kaadzos.pages.dev by the `iso` Pages branch alias, and the `R2_PUBLIC_URL` variable is set to that origin.
- The optional APT archive is a signed deb822 repository built by `ci/build-apt-repo.sh` and published by the tag-only `apt-repo` job to Cloudflare R2 under `apt/`; `ci/test-apt-repo.sh` builds a throwaway signed repo with an ephemeral key and makes apt install from it in a trixie container on every build push. The first package is `kaadzos-pack-defs` (the canonical `packs/` tree at `/usr/share/kaadzos/packs`), built by `ci/build-pack-defs.sh`; its version matches the release tag. Publishing requires `CLOUDFLARE_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `APT_GPG_PRIVATE_KEY` and the `R2_PUBLIC_URL` variable, and skips cleanly without them. The same key signs the release checksum (`KaadzOS-trixie-amd64.iso.sha256.asc`). The ISO ships the keyring only when `APT_GPG_PRIVATE_KEY`, the R2 credentials and `R2_PUBLIC_URL` are present at build time; a generated chroot hook (after package installation) writes the source stanza only if the published `InRelease` is reachable, so the ISO build never queries an unpublished archive and the base image never depends on the optional one. The public archive origin is https://iso.kaadzos.pages.dev (the `iso` Pages branch alias), and the `R2_PUBLIC_URL` variable is set to it.
- CI scope: `build.yml` ignores `site/**`, `iso-site/**`, `.github/workflows/site.yml`, `docs/**` and `**/*.md` on branch pushes, because those paths cannot change the ISO; `site.yml` remains the only workflow for website and ISO-host changes. Tag pushes are never path-filtered, so a release still re-runs the complete matrix, and `workflow_dispatch` still forces a run.
